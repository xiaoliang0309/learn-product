# SETNX 自旋锁：50 线程抢 10 件库存 · 时序图

> 场景：`POST /lock/test?mode=SETNX&stock=10&concurrency=50`
> 库存 10 件，50 个线程同时抢，SETNX 锁保证「读-改-写」同一时刻只有一个线程执行。

## 一、整体时序（简化成 3 个线程示意，50 个同理）

```
        主线程              线程T1             线程T2             线程T3            Redis
          │                   │                  │                  │                │
  发令枪响 │                   │                  │                  │                │
  ────────┼──────────────────→│                  │                  │                │
          │───────────────────┼─────────────────→│                  │                │
          │───────────────────┼──────────────────┼─────────────────→│                │
          │                   │                  │                  │                │
          │      putIfAbsent(lock) = true ✅抢到  │                  │                │
          │                   ├─────────────────────────────────────────────────────→│ SET lock NX EX → OK
          │                   │                  │                  │                │
          │                   │ 读库存 stock=10   │                  │                │
          │                   │ sleep(50ms) 干活中│  putIfAbsent → false ❌没抢到      │
          │                   │                  ├──────────────────────────────────→│ key已存在 → nil
          │                   │                  │ sleep(20ms)等待  │  putIfAbsent → false ❌
          │                   │                  │  ↻ 自旋重试       ├────────────────→│ nil
          │                   │ 写回 stock=9      │                  │ sleep(20ms)     │
          │                   ├─────────────────────────────────────────────────────→│ SET stock=9
          │                   │ remove(lock) 释放🔓│                 │  ↻ 自旋重试      │
          │                   ├─────────────────────────────────────────────────────→│ DEL lock
          │                   │                  │                  │                │
          │                   │                  │ putIfAbsent → true ✅ 终于抢到      │
          │                   │                  ├──────────────────────────────────→│ SET lock → OK
          │                   │                  │ 读库存 stock=9    │                │
          │                   │                  │ sleep(50ms)       │                │
          │                   │                  │ 写回 stock=8      │                │
          │                   │                  │ remove(lock) 释放🔓│                │
          │                   │                  │                  │ putIfAbsent→true ✅
          │                   │                  │                  │ 读库存=8 → 扣到7 │
          │                   ▼                  ▼                  ▼                ▼
        …… 依次排队，10 件库存被前 10 个线程各扣 1 件，最终精确扣到 0，第 11 个起 stock<=0 返回-1
```

## 二、关键阶段拆解

### 阶段1：发令枪响，50 线程同时冲
```
startGun.countDown()  →  50 个线程同一瞬间从 startGun.await() 放行
                          ↓
                   都执行 deductWithSetnxLock()
                          ↓
                   都调 trySetnxLock(lock, 10, 3000)
```

### 阶段2：只有 1 个线程抢到锁（SETNX 的原子性起作用）
```
T1: putIfAbsent(lock,...) ──→ Redis: SET lock val NX EX  →  key不存在 → 写入成功 → true ✅
T2: putIfAbsent(lock,...) ──→ Redis: SET lock val NX EX  →  key已存在 → 写入失败 → false ❌
T3: putIfAbsent(lock,...) ──→ Redis: SET lock val NX EX  →  key已存在 → 写入失败 → false ❌
...（其余47个线程也都是 false）
```
> **核心**：`SET NX` 是原子命令，50 个并发请求打到 Redis，**只有第 1 个能写入成功**，这就是锁能互斥的根因。Redis 单线程处理命令，天然串行化。

### 阶段3：抢到的干活，没抢到的自旋等待
```
T1（抢到）:  读库存 → sleep(50ms 模拟业务) → 写回库存-1 → remove(lock) 释放
T2~T50（没抢到）:
     ┌─ while 还没到 3 秒 ─────────────────┐
     │  putIfAbsent → false                │
     │  sleep(20ms)   ← 礼貌间隔，别刷爆Redis │
     │  ↻ 再回到循环开头重试                 │
     └──────────────────────────────────────┘
```

### 阶段4：锁释放，下一个自旋的线程抢到
```
T1 remove(lock) 释放锁
     ↓ 约 20ms 内
T2 自旋中再次 putIfAbsent → key已不存在 → 写入成功 → true ✅ 抢到
T2 干活、扣库存、释放 → T3 抢到 → …… 排队依次进行
```

### 阶段5：库存耗尽，后来者返回 -1
```
前 10 个抢到锁的线程：库存 10→9→8→…→1→0，各扣 1 件 ✅
第 11 个及以后抢到锁的线程：读到 stock=0 → if(stock<=0) return -1（没库存）✋
最终：库存精确 = 0，successCount=10，无超卖 ✅
```

## 三、3 秒超时兜底

```
如果某个线程 3 秒内始终没抢到（比如前面线程干活太慢/锁没释放）：
     while(System.currentTimeMillis() < deadline) 条件不满足
     → 跳出循环
     → return false
     → deductWithSetnxLock 返回 -2（抢锁失败）
```
> 防止线程无限自旋卡死。压测里 50 线程 × 每个干活 50ms ≈ 最坏 2.5 秒，所以 3 秒超时刚好够用。

## 四、和另外两种锁的对比（同一场景）

| | Redisson tryLock | **SETNX 自旋（本文）** | @Lock4j |
|---|---|---|---|
| 抢锁命令 | Lua 脚本 + pub/sub | `SET NX EX` | 底层=Redisson |
| 没抢到怎么等 | 订阅锁释放通知，**被唤醒** | **每 20ms 主动问一次（轮询）** | 同 Redisson |
| 等待效率 | 高（事件驱动，不空转） | 较低（空转发请求） | 高 |
| 释放锁 | `unlock()`（校验持有者） | `remove(key)`（压测从简） | AOP 自动 |
| 代码侵入 | 中（手写加/释锁） | 中（手写+自旋） | 零（一个注解） |

> **为什么生产上"排队等锁"更推荐 Redisson 而不是 SETNX 自旋？**
> 50 个线程自旋 = 每 20ms 就有约 49 个无效 `SET NX` 打到 Redis，纯浪费。
> Redisson 是"锁一释放就精准唤醒下一个等待者"，没有空转。所以：
> - 要**排队等**（都要执行）→ Redisson / @Lock4j
> - 只**防重复**（抢不到就拒绝）→ qingo 那种不自旋的 SETNX 抢一次

## 五、一句话总结

> SETNX 自旋锁 = 「`SET NX EX` 原子抢锁（只 1 人成功）+ 没抢到就每 20ms 重试（排队）+ 3 秒超时兜底 + 干完 `DEL` 放人」。
> 它用最朴素的 Redis 命令实现了互斥，但轮询等待效率不如 Redisson 的唤醒机制——这就是它和方式②的真正差距。
